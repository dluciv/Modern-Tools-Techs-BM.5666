# Personal RAG — простая RAG-система

Локальное хранилище документов с поиском по смыслу и по словам: векторная
база (SQLite + sqlite-vec) рядом с каталогом файлов, добавление через скилл
OpenCode, поиск через веб-сервис или MCP.

    personal_rag/    каталог с документами (txt, md, pdf, docx, xlsx, pptx)
    data/            sqlite-база: метаданные, чанки, векторы, полнотекст
    .model_cache/    локальная модель эмбеддингов (качается один раз)

## Зачем

Агент из `../simplest_AI_agent` умеет отвечать на вопросы, но не умеет
**искать по своим документам**: его контекст конечен, а документов может
быть больше. RAG (Retrieval-Augmented Generation) решает это просто:
перед ответом в контекст кладутся найденные фрагменты, и модель отвечает
по ним, цитируя источник. Модель не «знает» ничего сверх того, что нашлось,
— поэтому ответ всегда можно проверить.

В примере три части, и каждая показывает своё:

| часть | как устроена | что показывает |
|---|---|---|
| хранилище | SQLite + sqlite-vec + FTS5 в одном файле | векторный поиск без сервера |
| добавление | скилл OpenCode + `rag_tool.py` | модель сессии пишет аннотации |
| поиск | Flask-сервис и MCP-сервер | один и тот же код на двух транспортах |

## Файлы

    rag_config.py    конфигурация: TOML + переменные окружения + ключ из файла
    rag_text.py      морфология (pymorphy3, snowball) и чанкинг
    rag_parse.py     разбор форматов: md/txt, pdf, docx, xlsx, pptx, pandoc
    rag_store.py     база: documents, chunks, vec0, FTS5, гибридный поиск
    rag_llm.py       клиент дешёвой модели и сборка ответа с цитатами
    rag_tool.py      CLI: inspect, add, update, remove, list, search, scan
    rag_service.py   веб-сервис: /health, /search, /ask, /documents
    rag_mcp.py       MCP-сервер: search, ask, documents
    skills/personal-rag/      скилл для OpenCode (добавление и обновление)
    config.toml      начальная конфигурация
    keys.env.example шаблон файла с ключом (сам keys.env в .gitignore)

## Настройка

Нужны `uv` (всё остальное он подтянет сам по `# /// script`) и ключ
OpenAI-совместимого API — он нужен только для `/ask`, сам поиск работает
без сети. Пошагово:

    # 1. ключ API в отдельный файл (в .gitignore, не уезжает в git)
    cp keys.env.example keys.env && $EDITOR keys.env
    #    в файле строка: RAG_API_KEY=sk-...

    # 2. документы в каталог (можно симлинками на свои каталоги)
    ln -s ~/Документы/курс catalog/курс

    # 3. проверить, что конфиг читается и база видна
    uv run --script rag_tool.py list

Первый запуск качает модель эмбеддингов (~500 МБ) в `.model_cache`,
дальше всё офлайн.

### config.toml по секциям

Пути в конфиге считаются **от каталога самого конфига**, а не от текущей
директории запуска — иначе сервис, запущенный из systemd или cron, не
нашёл бы каталог. `~` раскрывается.

| секция | ключи | что делать |
|---|---|---|
| `[catalog]` | `dir`, `follow_symlinks` | каталог документов; симлинки-подкаталоги обходятся с защитой от петель |
| `[store]` | `dir` | где лежит `rag.sqlite3` (по умолчанию `data/`) |
| `[embedding]` | `model`, `cache_dir` | локальная ONNX-модель; размерность 384 фиксируется в базе при создании |
| `[llm]` | `base_url`, `model`, `key_file`, `timeout`, `max_tokens`, `max_tokens_limit`, `temperature` | дешёвая модель для `/ask`; ключ читается из `keys.env` |
| `[search]` | `vector_weight`, `bm25_weight`, `candidates`, `max_distance`, `chunk_chars` | баланс гибрида, размер чанка (1200 символов) |
| `[service]` | `log_file` | журнал (пусто — только терминал) |

Что обычно трогают:

* **другой провайдер для `/ask`** — `[llm] base_url` и `model`, ключ в
  `keys.env`; подойдёт любой OpenAI-совместимый эндпоинт;
* **свой каталог** — `[catalog] dir` или симлинк внутрь каталога
  (симлинки удобнее: каталог в git не уезжает, ссылки локальные);
* **более строгий поиск** — поднять `search.max_distance` (ловит больше
  мусора, но теряет далёкие ответы) или `search.chunk_chars` (короче
  чанк — точнее цитата, больше фрагментов);
* **перенос на другой машину** — скопировать `catalog/`, `data/` и
  `.model_cache/`; без кэша модель скачается заново.

Любой ключ можно переопределить переменной окружения (приоритет выше
файла): `RAG_CATALOG_DIR`, `RAG_STORE_DIR`, `RAG_BASE_URL`, `RAG_MODEL`,
`RAG_API_KEY`, `RAG_LOG_FILE`, `RAG_CONFIG`, `RAG_PORT`.

## Как устроено хранение

Один sqlite-файл `data/rag.sqlite3` с четырьмя таблицами:

    documents    путь, название, оглавление (toc), аннотация, хеш, размер
    chunks       куски текста по 1200 символов с перекрытием
    chunks_vec   vec0: вектор float[384] на чанк, косинусное расстояние
    chunks_fts   FTS5: леммы и исходный текст чанка

Размерность векторов (384) фиксируется при создании базы в `PRAGMA
user_version`. Сменить модель на модель другой размерности без пересоздания
базы нельзя — при несовпадении сервис отвечает понятной ошибкой, а не
пустыми результатами.

## Как устроен поиск

Гибридный, потому что ни один способ в одиночку не работает хорошо:

1. **BM25 по FTS5** — точные слова и словоформы. Сильное место: имена,
   код, канцелярит, аббревиатуры, которых нет в обучающей выборке
   эмбеддингов.
2. **kNN по vec0** — смысловое сходство по косинусу. Работает с синонимами
   и перефразированием, одинаково для русского и английского.
3. **Слияние через RRF** (reciprocal rank fusion): каждый кандидат получает
   сумму `w / (60 + ранг)` по каждому списку. RRF не требует калибровки —
   баллы BM25 и косинуса несопоставимы по шкале, а ранги сопоставимы всегда.

Что добавлено поверх «чистого» гибрида:

* **Лемматизация с обеих сторон.** FTS5 не знает русской морфологии:
  «кошки», «кошку» и «кошек» — три разных слова. pymorphy3 сводит их к
  «кошка» при индексации и при запросе; для английского — Snowball-стеммер
  (walking, walked, walks → walk). Разбор идёт по словам, поэтому
  смешанный текст обрабатывается верно.
* **Порог `search.max_distance`.** kNN обязан вернуть ровно k ближайших
  векторов, даже для бессмысленного запроса («цвет неба сегодня» дал бы три
  фрагмента про регламент отпусков). Порог 0.8 отсекает такой мусор,
  но фрагмент, подтверждённый дословным совпадением слов в BM25, остаётся
  в любом случае: расстояние 0.83 для короткого чанка — обычное дело.
* **Заголовок в индексе.** Термин может жить только в заголовке раздела
  («Зачем нужен чанкинг»), поэтому заголовок идёт первой строкой и в FTS,
  и в эмбеддинг. В базе хранится чистый текст — цитаты остаются подлинными.

## Как система говорит «не найдено»

BM25 ищет по OR: запрос «квантовые вычисления» находит фрагменты по слову
«вычисления» — про распределённые вычисления, а не про квантовые. Без
проверки тема несуществующая выглядит как найденная.

Поэтому запрос разбирается по словам (`Store.query_terms`): каждое слово
ищется в корпусе отдельно — по лемме, а если точного совпадения нет, то
по основе слова (`rag_text.stem`), что снимает расхождения словоформ
(«Гёделя» → «гедель», «криптография» → «криптографический»).

Дальше работают два уровня:

* **Флаж `not_found`** — самое редкое слово запроса в корпусе не
  встречается, значит темы, скорее всего, нет. Флаж **не блокирует**
  поиск: лексика не знает синонимов, и «нейросети» в корпусе есть как
  «нейронные сети».
* **Вердикт модели.** Ответ без единой цитаты `[1]` означает, что в
  фрагментах ответа не было. Тогда в ответе — `found: false`, а
  `sources` пуст: список источников к ответу «ничего не нашлось»
  выглядит как подтверждение ответа и вводит в заблуждение.

Раньше «не найдено» означало «в документах нет ответа», но в ответе всё
равно висел список из двадцати нерелевантных источников. Теперь
пользователь видит честное «не найдено» — без источников.

## Кто что пишет: две модели

В примере намеренно две разные модели, и это ключевая мысль:

* **модель сессии OpenCode** пишет аннотации и названия при добавлении.
  Это та же модель, что отвечает пользователю, — отдельный сервис и ключ
  для аннотаций не нужны, а качество описаний такое же, как у ответов
  агента. Скилл как раз говорит агенту: посмотри сводку (`inspect`),
  напиши аннотацию, передай её в `add --annotation`.
* **дешёвая модель из конфига** отвечает на `/ask`. Поиск должен быть
  дешёвым, поэтому туда ставится недорогая модель; для `/search` она не
  нужна вообще.

## Как пользоваться: CLI

`rag_tool.py` — тот же интерфес, что использует скилл; им можно
обходиться и без OpenCode (в скриптах, cron, при отладке):

    uv run --script rag_tool.py inspect путь/к/файлу.md   # что это за файл
    uv run --script rag_tool.py add путь --annotation "…" # добавить в базу
    uv run --script rag_tool.py update путь               # перечитать (по хешу)
    uv run --script rag_tool.py update путь --force       # пересчитать принудительно
    uv run --script rag_tool.py remove путь|id            # убрать из базы
    uv run --script rag_tool.py list                      # что индексировано
    uv run --script rag_tool.py search "запрос" -k 5      # поиск без сервиса
    uv run --script rag_tool.py scan                      # сверка каталога и базы
    uv run --script rag_tool.py scan --apply              # применить расхождения
    uv run --script rag_tool.py plan КАТАЛОГ -o plan.json # манифест по каталогу
    uv run --script rag_tool.py apply plan.json           # загрузить по манифесту
    uv run --script rag_tool.py reindex --all             # пере-чанковать всё
    uv run --script rag_tool.py prune                     # убрать осиротевшие векторы

У всех команд есть `--json` (читаемый JSON вместо текста), `--no-json`
отключает его, `--config` указывает другой конфиг, `--no-log` / `--log-file`
управляют журналом. Файл вне каталога `add` скопирует сам; конфликт имён
разрешит суффиксом, не затирая чужой. Удаление убирает только запись из
базы, файл на диске остаётся.

### Пакетная загрузка каталога: plan → разметка → apply

Загрузка папки вручную (по файлу на `inspect` + `add`) упирается в контекст
сессии: сводки по сотне документов её съедают. Поэтому работа разделена
пополам: механику делает инструмент, содержание — модель.

    # 1. Прочитать каталог и описать каждый файл (в базу ничего не пишется)
    uv run --script rag_tool.py plan Набор-2026 -o plan.json --split 4

    # 2. Вписать аннотации в plan.json (или в каждую plan.part-N.json):
    #    руками, либо субагентами rag-annotator — по части на агента,
    #    тогда правки не пересекаются. Единственное место, где нужен
    #    смысл: что это за документ и чем полезен.

    # 3. Загрузить всё одним процессом (модель эмбеддингов грузится один раз)
    uv run --script rag_tool.py apply plan.json
    # или несколько частей:
    uv run --script rag_tool.py apply plan.part-*.json

В записи манифеста: `rel`, `title`, `lang`, `chars`, `chunks`, `toc`,
`head` (первые 2500 знаков текста, `--head-chars` меняет) и пустая
`annotation`. Запись без аннотации в базу не кладётся — она попадает в
`missing_annotation`, команда возвращает ненулевой код, и список таких
путей печатается. Уже лежащий в базе файл с тем же хешем пропускается
(`--force` — перезаписать). Ошибки разбора попадают в `failed` и не
останавливают остальные.

`plan` при `--split N` рядом с `plan.json` пишет `plan.part-1.json …` —
по части манифеста на разметчика, без пересечений правок. Без `-o` вместе
с `--split` команда откажется: частям нужен адрес.

### reindex: когда менялся парсер

`scan --apply` и `update` сверяют хеши файлов, а не то, как файл разбирается.
После правки `rag_parse.py` (другая нарезка на чанки, распознавание
заголовков) хеши те же, и переиндексации не происходит — в базе остаётся
старая нарезка. В этом случае:

    uv run --script rag_tool.py reindex --all             # только текст и чанки
    uv run --script rag_tool.py reindex --all --titles    # заодно пересчитать названия
    uv run --script rag_tool.py reindex путь/к/файлу.docx # один файл

Аннотации, id и хеши сохраняются; `--titles` дополнительно перезаписывает
названия значениями из парсера — его включают только когда авто-заголовки
действительно исправлены и старые названия не нужны (по умолчанию названия
не трогаются, чтобы не затереть ручные правки через `--title`).

### prune: осиротевшие векторы

Виртуальные таблицы `chunks_vec`/`chunks_fts` не умеют каскадного удаления.
В старой версии `upsert` удалял строки `chunks` и не трогал их — в базе
оставались векторы без чанка (6102 штуки накопилось за две переиндексации).
Такие строки мешают kNN-выдаче и раздувают файл. Теперь `upsert` чистит их
сам, а `prune` убирает уже накопившиеся:

    uv run --script rag_tool.py prune     # удалённые сироты, ничего не пересчитывая

Команда идемпотентна: второй запуск находит ноль строк. Если в ответе
`chunks_without_vec` не ноль — есть чанки без вектора, их даст `reindex`.

## Добавление через скилл OpenCode

Скилл лежит в `skills/personal-rag/SKILL.md`. Подключить его — либо симлинком
в каталог скиллов (так сделано в этом окружении):

    ln -s $PWD/skills/personal-rag ~/.config/opencode/skills/personal-rag

либо каталогом в конфиге OpenCode (тогда доступен только в проектах
с этим конфигом):

    # opencode.jsonc проекта
    "skills": ["/абсолютный/путь/к/examples/AI/personal_rag/skills"]

После этого «положи этот файл в базу», «обнови документ», «убери из базы»
подхватывает скилл, и агент делает нужную последовательность:

    inspect файл     → название, оглавление, язык, начало текста (JSON)
    add файл --annotation "…"   → копирование в каталог, разбор, эмбеддинги
    update файл      → перечитать; если хеш тот же — не тратить эмбеддинги
    remove файл|id   → удалить из базы (файл на диске остаётся)
    scan [--apply]   → что в каталоге нового, изменённого, пропавшего
    plan КАТАЛОГ -o plan.json [--split N] → манифест по всей папке
    apply plan.json  → загрузить всё по манифесту (аннотации обязательны)
    reindex [--all] [--titles] → пере-чанковать после правки парсера

Содержательную часть пакетной загрузки (аннотации по манифесту) скилл
отдаёт субагенту `rag-annotator` (файл `agents/rag-annotator.md` рядом с этим
README; в `~/.config/opencode/agents` он виден через симлинк каталога):
основная сессия запускает `plan`, раздаёт части и вызывает `apply`, а
контекст не заполняется сводками по сотне документов. На небольшом числе
файлов аннотации пишет сама сессия — субагент не обязателен.

Куда указывает `rag_tool.py` скилл узнаёт из переменной окружения
`PERSONAL_RAG_DIR` (каталог personal_rag); если она не задана, скилл
считает, что OpenCode запущен в самом каталоге personal_rag. Поэтому
добавлять и удалять документы можно из любого проекта:

    # один раз в ~/.zshrc (или в env-секции конфига OpenCode)
    export PERSONAL_RAG_DIR=$HOME/_/work/SPbU/courses/Modern-Tools-Techs-BM.5666/examples/AI/personal_rag

`config.toml` ищется рядом с `rag_tool.py`, а не в текущей директории:
база и каталог документов всегда те, что в конфиге.

Файл вне каталога инструмент скопирует сам; конфликт имён разрешит
суффиксом, не затирая чужой файл. Симлинки на подкаталоги обходятся
с защитой от петель.

## Поиск через веб-сервис

    uv run --script rag_service.py              # 127.0.0.1:8081
    uv run --script rag_service.py --port 9000 --host 0.0.0.0
    uv run --script rag_service.py --no-log     # без журнала

    curl 'http://127.0.0.1:8081/health'
    curl 'http://127.0.0.1:8081/search?q=эскалация&k=3'
    curl -X POST http://127.0.0.1:8081/ask -H 'Content-Type: application/json' \
         -d '{"q":"когда возможна повторная эскалация","k":3}'
    curl 'http://127.0.0.1:8081/documents'

`/search` отдаёт сырые фрагменты с путями, весами и рангами обеих сторон —
по ним видно, почему ответ получился таким. Плюс `not_found` и
`missing_terms`: если темы в каталоге нет, об этом сказано прямо, а не
замаскировано чужими фрагментами. `/ask` прогоняет фрагменты через
дешёвую модель и возвращает готовый ответ с источниками `[1]`, `[2]`;
если ответа в документах нет — `found: false` и пустые `sources`; если
модель недоступна — код 502 и фрагменты в том же ответе.

Журнал пишется в терминал и (при `log_file` в конфиге) в файл построчно
JSON — как в агенте и в Элизе.

## Поиск через MCP

    # opencode.json или opencode.jsonc
    "mcp": {
      "servers": {
        "personal-rag": {
          "type": "local",
          "command": ["uv", "run", "--script",
                      "/путь/к/examples/AI/personal_rag/rag_mcp.py"]
        }
      }
    }

Инструменты `search`, `ask`, `documents` — те же функции, что использует
curl-сервис: MCP здесь просто ещё один транспорт, а не отдельная система.

## Известные ограничения

* **PDF с кернингом** может дробить слова (pypdf: «дней» → «днеи» + хвост).
  Для справочного поиска хватает, для дословных цитат — нет.
* **Сканы без OCR** не извлекаются: инструмент честно сообщает об этом
  вместо того, чтобы класть в базу пустой документ.
* **Код парсера изменился** — уже проиндексированные документы обновятся
  только по `update --force` или `scan --apply` (обычный `update`
  смотрит на хеш файла и честно отвечает «файл не изменился»).
* **Обработка в один поток.** Сервис использует `threaded=False`: база —
  один sqlite-файл, а модель эмбеддингов не рассчитана на параллельные
  вызовы. Для справочного сервиса одного потока хватает.
