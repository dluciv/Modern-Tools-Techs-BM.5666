# Personal RAG: работа с документальным хранилищем

Этот скилл — про добавление документов в личное RAG-хранилище,
обновление и удаление. **Поиск — не через скилл**: он идёт через
веб-сервис (`rag_service.py`) или MCP-сервер (`rag_mcp.py`), см. README.

## Главное правило: аннотацию пишешь ты

Инструмент сам ничего не выдумывает: он обходит каталог, разбирает файл
(название, структура, оглавление, текст), копирует файл, режет на чанки и
считает эмбеддинги. **Аннотацию (2-4 предложения) и, если нужно, название —
пишешь ты, модель сессии** (или субагент `rag-annotator`, если документов
много). Так в базу попадает осмысленное описание, а не первая
попавшаяся строка файла.

## Директория системы

Инструмент лежит в директории personal_rag. Определи директорию через
переменную скилла `RAG_DIR` так:

    RAG_DIR="${PERSONAL_RAG_DIR:-.}"

`PERSONAL_RAG_DIR` — переменная окружения, указывающая на каталог
personal_rag; её обычно задают один раз в профиле или в конфиге OpenCode
проекта. Если переменной нет — считается, что OpenCode запущен в самом
каталоге personal_rag (или что он лежит в текущем каталоге).

`config.toml` ищется рядом с `rag_tool.py`, а не в текущей директории:
каталог документов и база всегда те, что записаны в конфиге, откуда бы
скилл ни запускался.

Проверь, что директория найдена, — первая же команда:

    "$RAG_DIR/rag_tool.py" list

Если файла нет и `PERSONAL_RAG_DIR` не задана — спроси у пользователя,
где лежит personal_rag, и не угадывай путь сам.

> **Ловушка zsh:** нельзя называть переменную `path` — в zsh `path`
> связана с `PATH` (правишь одно, меняется другое), и команда падает
> непонятной ошибкой. Пиши `src`, `file`, `target`.

## Один документ

1. Покажи сводку, ничего не записывая:

   ```bash
   "$RAG_DIR/rag_tool.py" inspect путь/к/файлу.md
   ```

   В ответе: `title`, `toc` (оглавление), `lang`, `chars`, `head`
   (начало текста). По ним и пиши аннотацию — весь файл читать не нужно.
   Если в `warning` сказано, что файла нет или это скан — скажи об этом
   пользователю и остановись.

2. Напиши аннотацию: 2-4 предложения на языке документа, по существу
   (что это, о чём, чем полезно). Не пересказывай заголовки — добавь то,
   чего в них нет.

3. Положи в базу:

   ```bash
   "$RAG_DIR/rag_tool.py" add путь/к/файлу.md --annotation "…" [--title "…"]
   ```

   `--title` нужен, только если название в документе плохое (например,
   «Протокол» вместо «Протокол совещания 12.03»). Файл вне каталога
   документов инструмент скопирует сам; тот же файл, уже лежащий в
   каталоге, повторно не копируется, имя-конфликт он разрешит суффиксом.

## Целый каталог: plan → разметка → apply

Когда документов много (папка, набор файлов), не читай их по одному в
основной сессии — сначала пусть инструмент опишет всё разом, а ты наполнишь
только аннотации.

**1. План — ничего не записывает, только читает:**

```bash
"$RAG_DIR/rag_tool.py" plan КАТАЛОГ -o /tmp/rag-plan.json [--split 4]
```

В манифесте по каждому файлу: `rel`, `title`, `lang`, `chars`, `chunks`,
`toc`, `head` (первые 2500 знаков текста) и пустое `annotation`.
`--split N` дополнительно разрежет манифест на `plan.part-1.json … part-N`:
у каждого разметчика свой файл, правки не пересекаются. Файлов меньше N —
части не пустые не пишутся. Ошибки разбора (`errors`) скилл обязан
показать пользователю.

**2. Разметка — единственное место, где нужно думать о содержании.**

Аннотацию можно написать и самому, но на десятках файлов это быстро
заполняет контекст основной сессии. Правильный путь — раздать части
субагентам `rag-annotator` (параллельно, по одному субагенту на часть):

> Разметь часть манифеста `<путь к plan.part-2.json>`: заполни `annotation`
> для каждой записи (2-4 фразы на языке документа по `title`/`toc`/`head`),
> `title` поправь, только если он явно мусорный. Меняй только этот файл.

Если файл один-два — заполни аннотации прямо в основном сессионе сам,
без субагента.

**3. Apply — записывает всё в базу одним процессом:**

```bash
"$RAG_DIR/rag_tool.py" apply /tmp/rag-plan.json
# или несколько частей сразу:
"$RAG_DIR/rag_tool.py" apply /tmp/rag-plan.part-*.json
```

`apply` сам скопирует файлы в каталог, разберёт их, срежет на чанки и
посчитает эмбеддинги; модель эмбеддингов при этом грузится один раз на весь
список. Пустая `annotation` — запись попадёт в `missing_annotation`, таких
должно быть ноль; запись без аннотации в базу не кладётся. Документ, уже
лежащий в базе с тем же хешем, пропускается (`--force` — перезаписать).

Проверяй код возврата: ненулевой + `failed`/`missing_annotation` в JSON —
что-то не загрузилось, покажи список пользователю.

## Обновление

```bash
"$RAG_DIR/rag_tool.py" scan              # что изменилось в каталоге?
"$RAG_DIR/rag_tool.py" update путь/к/файлу.md
```

`update` сам замечает, что хеш файла тот же, и не тратит эмбеддинги
зря (`updated: false`). Если содержание изменилось существенно —
перепиши и аннотацию: `update … --annotation "…"`. `scan --apply`
переиндексирует изменённые файлы, оставив прежние аннотации, — это
быстрый путь, когда аннотации всё ещё верны.

## reindex: после правки парсера

Если менялся `rag_parse.py` (другая нарезка на чанки, распознавание
заголовков), хеши файлов не меняются — и `update`, и `scan --apply`
ничего не делают, а в базе остаётся старая нарезка. Тогда:

```bash
"$RAG_DIR/rag_tool.py" reindex --all            # только текст и чанки
"$RAG_DIR/rag_tool.py" reindex --all --titles    # заодно пересчитать названия
```

Аннотации и id сохраняются в обоих случаях. `--titles` перезаписывает
названия спорными авто-значениями — по умолчанию его не включай: названия
могли поправить вручную. После `reindex` освежи сервис/MCP, если они уже
подняты, и проверь поиск: `search "…" `.

## Удаление

```bash
"$RAG_DIR/rag_tool.py" remove путь/к/файлу.md     # или remove 3 (по id)
```

Удаляется запись из базы, сам файл в каталоге остаётся. Если пользователь
просит «удали файл» — уточни: из базы или с диска. Скилл удаляет только
из базы; с диска файл удаляет сам пользователь.

## Что проверять после любой команды

Все команды печатают JSON. Проверяй:

- `added.chunks` / `doc.chunks` — если 0, текст не извлекся (скан?),
  сообщи пользователю;
- `warning` в `inspect`, `errors` в `plan` — предупреждения инструмента;
- код возврата: ненулевой и текст в stderr — команда не прошла, причина
  в stderr, повтори её не нужно, скажи пользователю.

Не запускай `add`, `apply`, `reindex` параллельно: база — один sqlite-файл,
одновременные записи в неё ни к чему. `plan` писать не может, его можно
запускать хоть параллельно.
